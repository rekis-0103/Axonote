# Architecture

## Overview

Axonote is a monorepo with three runtime services backed by MySQL. Heavy document processing is offloaded to a worker so the API stays responsive and isolated from untrusted file parsing.

```
┌──────────────┐   HTTPS/JSON    ┌──────────────┐   enqueue (DB)   ┌──────────────┐
│  apps/web    │ ──────────────► │  apps/api    │ ───────────────► │ apps/worker  │
│  Next.js     │ ◄────────────── │  FastAPI     │ ◄─────────────── │  Python NLP  │
└──────────────┘   poll job/sumr └──────┬───────┘   update status  └──────┬───────┘
                                        │                                  │
                                        ▼                                  ▼
                                 ┌──────────────┐                  uploads/ (shared
                                 │   MySQL 8.x  │                  filesystem volume)
                                 └──────────────┘
```

## Components

- **apps/web** — presentation only. Auth UI, dashboard, upload, summary view, quiz UI, history. Talks to the API via JSON; polls `GET /jobs/{id}` for analysis progress. No parsing or NLP client-side.
- **apps/api** — control plane. Auth, upload intake, material CRUD, job creation, summary/question reads, quiz attempts, scoring, security middleware. Owns the DB schema (Alembic).
- **apps/worker** — compute plane. Polls the `jobs` table, runs the analysis pipeline, writes summary + questions, updates material/job status. Stateless and idempotent.
- **MySQL** — single source of truth for users, materials, jobs, summaries, questions, attempts.

## Analysis pipeline (worker)

```
material file (uploads/)
  -> extract text        (pypdf / python-docx / python-pptx)
  -> preprocess English  (clean, sentence split, tokenize, stopword removal)
  -> chunking            (split into manageable segments)
  -> keyword extraction  (TF-IDF over sentences/terms)
  -> sentence ranking    (TextRank via NetworkX similarity graph)
  -> summary generation  (top-ranked sentences, original order)
  -> question generation (cloze/MCQ from key sentences + keyword + distractors)
  -> persist + status = ready  (or failed with error_message)
```

## Job lifecycle (DB-backed queue)

```
material.status:  pending -> processing -> ready | failed
job.status:       queued  -> running    -> done  | failed
```

The worker claims jobs with `SELECT ... FOR UPDATE SKIP LOCKED` (MySQL 8) so multiple workers never double-process. Jobs are idempotent: re-running replaces prior summary/questions for the material.

## Data flow

1. User authenticates → access + refresh tokens.
2. `POST /materials` (multipart) → file validated, stored with random name, row created `pending`.
3. `POST /materials/{id}/analyze` → creates a `queued` job.
4. Worker claims job → `running` → pipeline → writes summary + question set → material `ready`, job `done`.
5. Web polls `GET /jobs/{id}` until terminal state.
6. `GET /materials/{id}/summary` and question set rendered.
7. `POST /question-sets/{id}/attempts` → answers scored, attempt stored, history available.

## Tech decisions

- **No LLM** for MVP — extractive summary (TextRank) + rule-based MCQ generation.
- **DB-backed jobs** instead of Celery/Redis for MVP simplicity; can swap later behind the same `jobs` table.
- **English-only** preprocessing for MVP.
- **MCQ-only** questions, but schema carries a `type` column for future expansion.
- **packages/shared** is the TypeScript contract for the web app; the canonical cross-language contract is the OpenAPI schema generated by FastAPI plus [`api-contract.md`](api-contract.md).

## Failure modes

- Corrupt/unparseable file → job `failed`, `material.error_message` set, surfaced in dashboard.
- Worker crash mid-job → job stays `running`; a reaper requeues jobs exceeding a timeout (future).
- Oversized/wrong-type upload → rejected at API before storage.
